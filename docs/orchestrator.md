# Orchestrator runbook (read this when told to run a phase)
You coordinate; you do not implement. All code changes go through the phase-implementer subagent. Keep your own context small: read reports, not diffs.

1. Read docs/PROGRESS.md (state, open items, earlier decisions) and the phase prompt you were given. Check that the working tree is clean.
2. Write a briefing: phase prompt path, plan sections, applicable earlier decisions, the escalation list below. Call phase-implementer with model sonnet and effort medium (always medium, unless the user says otherwise).
3. If it returns NEEDS_DECISION, accept a recommendation only if it matches docs/plan.md and CLAUDE.md exactly; a "recommended" option may deviate from the plan, so check each one. If it matches, decide and log it as a row in the PROGRESS.md Decisions table with "[auto]" before the decision text. If it is on the escalation list, or the plan is silent or contradicts it, ask the user with AskUserQuestion (options plus your recommendation), then call the implementer again with the answers and "resume after the last commit".
4. On STATUS: DONE, validate yourself: git status is clean and git log shows the commit units; run `make up` if Postgres is not running, then make check and make test-int with output redirected to a file, exit code first; map every "Done when" item to its evidence in the report and re-run the one or two cheapest commands that prove it; make no real LLM calls. For phases 1.4b, 2.3, 3.3, 3.4 and gates 1.8, 2.6 also call the phase-verifier subagent (model sonnet, effort medium).
5. On a failure send the exact failing output back to the implementer once. If it fails again, stop and report to the user.
6. If everything is green and nothing is escalated, tell the user in at most 10 lines: what was built, the evidence, auto decisions made, open items. Do not merge until the user says so. Gates 1.8 and 2.6 are never merged without an explicit user decision. Then stop; start another phase only if told ("run phases X and Y in sequence" is allowed; stop at the first escalation).

Always escalate to the user: DB schema or migration, public API, new dependencies, cost (including any real LLM calls beyond 5 and any paid-tier use), thresholds and gates, deviations from docs/plan.md, anything touching data/real, eval/reference or .env, destructive git or machine-level changes, and any ambiguity between two reasonable readings of the plan.
