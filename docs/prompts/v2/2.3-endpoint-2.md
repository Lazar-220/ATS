# Phase 2.3: Endpoint 2 (rank the CV database)

**Read first:** §1.2, §2.0, §2.4 ("Per endpoint 2 call"), §5.2 (prefilter and rank rows), §6.1 (free-tier bullets), §6.3 (RAM rules) of `docs/plan.md`.
**Depends on:** 2.2.
**Branch:** `phase/2.3-endpoint-2`

## Goal

`POST /rankings/search` takes a posting PDF, picks the top N candidates from the database with an
embedding prefilter, judges only those, and returns the top K.

## Build (commit units)

1. **`feat(search): add per-requirement candidate prefilter`**
   For each candidate: `Σ wᵢ · maxⱼ cos(requirementᵢ, chunkⱼ) / Σ wᵢ` over that candidate's chunks.
   One SQL query returns the top N with their prefilter score. While the database holds N
   candidates or fewer, all of them go on.

2. **`feat(worker): add search job that judges only candidates without a current assessment`**
   The job sets up the position if the posting is new, runs the prefilter, writes
   `request_candidate` rows with the prefilter score, and enqueues judge jobs only for candidates
   that have no completed assessment for the current `rubric_version`.

3. **`feat(api): add POST /rankings/search with a deadline and partial results`**
   Optional `top_n` (default 20) and `top_k` (default 10). The API enqueues the search job and
   waits for the result up to a deadline (default 120 s, in configuration). On timeout it returns a
   partial ranking with a status per candidate, and the remaining assessments finish in the background.
   Ordering as in the interface: no failed mandatory requirement first, then score.

4. **`feat(eval): add prefilter recall and ranking metrics`**
   Prefilter recall@N: the share of candidates with relevance ≥ 2 that enter the top N, measured
   separately from the final rank. Final rank: NDCG@10, precision@5 with relevance ≥ 2, Kendall tau.

5. **`feat(web): add database search screen`**
   Upload a posting, choose N and K, see the top K with status per candidate and the same assessment view as 1.5.

## Out of scope

Batch import (2.4), HNSW (2.5), score ranges while waiting for HR (v3).

## Done when

- [ ] Prefilter recall@N ≥ 0.95 on the golden set. With 60–90 CVs, N = 20 is close to the whole
      pool, so report recall at N = 5, 10 and 20.
- [ ] NDCG@10, precision@5 and Kendall tau are measured and recorded.
- [ ] One endpoint call makes at most N judge calls (test with the fake client).
- [ ] A second call with the same posting makes zero judge calls.
- [ ] A call that exceeds the deadline returns a partial ranking, and the missing assessments are complete in the database later.
- [ ] The API process still loads no model.

## Traps

- The API must not embed the posting itself. The embedding model lives in the worker (§6.3), so the
  endpoint enqueues and waits.
- On the free tier, 5 requests per minute cannot cover N = 20 within 120 s (§1.2). For manual trials use `top_n` 3.
- One vector per CV against one vector per posting measures topic, not requirements (§1.2). The
  prefilter is per requirement; do not simplify it.
- Decide how the API learns the job is finished (polling or LISTEN/NOTIFY), and tell me the trade-off before building.
