# Phase 2.1: Chunking and embeddings

**Read first:** §2.1, §2.2, §2.3, §6.2, §6.3 (RAM budget) of `docs/plan.md`; `docs/schema.sql` if it exists.
**Depends on:** v1 gate passed (1.8).
**Branch:** `phase/2.1-chunking-embeddings`

## Goal

Every CV in the database has chunks with vectors, every requirement has a vector, and changing
the embedding model is a configuration change plus one command.

## Build (commit units)

1. **`feat(db): add vector extension, chunk table and requirement embeddings`**
   Migration: the `vector` extension; the `chunk` table with the metadata from §2.3 and a
   1024-dimension vector; a vector and `embedding_model` on `requirement`. The `tsvector` column is
   built from normalized text with Postgres's `serbian` configuration. No ANN index: search is exact until 2.5.

2. **`feat(pipeline): build chunks from parsed cv items with context headers`**
   One chunk per parsed item, not per slice of text. Each chunk gets a header before embedding,
   in the form "Work experience | Project Manager, bank | 2019-03 to 2023-06 (51 months)".
   The skills list is one chunk plus a `skills[]` array normalized through an alias table, so that
   "C#", "C++" and "C" stay distinct and "Node.js" matches "node". A document that carries the
   coverage flag from 1.4a falls back to paragraph splitting: about 300 tokens, 15% overlap.

3. **`feat(worker): embed chunks and requirements with a local model`**
   `sentence-transformers` with `EMBEDDING_MODEL` (default `BAAI/bge-m3`), loaded lazily and only
   in the worker. Embed the original text with its header, not the normalized text. Requirements
   are embedded at position setup.

4. **`feat(worker): make ingest idempotent and add backfill and reindex`**
   `content_hash` prevents duplicate chunks and repeated embedding on re-upload. A backfill command
   chunks and embeds every CV and requirement stored in v1. `make reindex` re-embeds everything for
   the configured model. A search never mixes vectors of two models: filter by `embedding_model`.

## Out of scope

Search and retrieval (2.2), endpoint 2 (2.3), HNSW (2.5), the reranker (2.2).

## Done when

- [ ] Every CV and every requirement in the database has vectors after the backfill, with no re-upload.
- [ ] Uploading the same CV again creates no chunks and computes no embeddings.
- [ ] Switching `EMBEDDING_MODEL` and running `make reindex` leaves no chunk on the old model in search results.
- [ ] The API process does not import the embedding library: checked by a test or by measured memory.
- [ ] Worker memory with the model loaded and embedding time per CV are recorded in `docs/PROGRESS.md`.
- [ ] A chunk's `char_start` and `char_end` point to its text in `raw_text` (test).

## Traps

- Install the CPU-only build of `torch`. The default wheel on Linux pulls several gigabytes of GPU
  libraries. Configure the index in `pyproject.toml` and tell me the download size before you start.
- The first model load downloads about 2.3 GB into the Hugging Face cache, outside the repository.
  Log it under "Machine state" in `docs/SETUP.md`.
- Check free memory before loading the model. Langfuse and the model do not fit together comfortably (§6.3).
- bge-m3 produces 1024 dimensions. The two alternative models in §6.2 do too, so the column fits all three.
