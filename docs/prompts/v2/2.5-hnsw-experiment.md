# Phase 2.5: HNSW experiment

**Read first:** §1.4 (the table and the paragraph after it) of `docs/plan.md`.
**Depends on:** 2.4.
**Branch:** `phase/2.5-hnsw-experiment`

## Goal

Measure, on this machine, at how many chunks an HNSW index beats exact search. This is an
experiment with a recorded result, not a feature.

## Build (commit units)

1. **`feat(bench): add vector search benchmark`**
   A script that fills a scratch table with synthetic 1024-dimension vectors at several sizes
   (for example 5,000, 20,000, 50,000 and 100,000 chunks, spread over a realistic number of
   candidates), then measures two workloads with and without HNSW: a single query, and the
   endpoint 2 prefilter for one position with 12 requirements. Report p50 and p95 latency, index
   build time and size, and the recall of HNSW against the exact result.

2. **`docs(bench): record hnsw results and decision`**
   The table, the crossover point for each workload, and the decision: add the index now, or
   record the chunk count at which to add it.

3. **`feat(db): add hnsw index`** (only if the result justifies it and I confirm)

## Out of scope

Tuning beyond the default HNSW parameters and one alternative setting. Other index types.

## Done when

- [ ] The benchmark runs with one command and writes its results to a file.
- [ ] `docs/PROGRESS.md` states at how many chunks HNSW beats exact search on this machine, for both workloads.
- [ ] The decision is recorded with the numbers that support it.

## Traps

- Use a scratch database or schema. Never write synthetic vectors into the application tables.
- 100,000 vectors of 1024 dimensions take roughly 400 MB before the index. Check free disk and
  memory first, and drop the scratch data when done.
- The plan's reference numbers (§1.4) come from different hardware and Postgres 16. Expect different values.
- A filter on `candidate_id` changes how an ANN index behaves. Measure the filtered case, since that is how evidence search runs.
