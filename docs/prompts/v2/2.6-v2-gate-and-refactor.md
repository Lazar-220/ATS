# Phase 2.6: v2 gate and refactor before v3

**Read first:** §7 (gate diagram, "Refactor before v3"), §2.5, §3.1, §3.5 of `docs/plan.md`; `docs/schema.sql` if it exists; `docs/PROGRESS.md`.
**Depends on:** 2.5.
**Branch:** `phase/2.6-v2-gate-refactor`

## Goal

Two parts, in this order. First decide with numbers whether v2 is done. Then, only if it is,
reshape the data model and the service layer so v3 can be built on them, without changing behavior.

## Part 1: the gate

Run the retrieval and ranking evals on the test split (show the dry run, wait for my confirmation).

- Evidence recall@5 ≥ 0.9.
- Prefilter recall@N ≥ 0.95.
- NDCG@10 recorded.

Use the phase-verifier subagent on each v2 phase prompt. Record the result in `docs/PROGRESS.md`
as PASSED or NOT PASSED. If NOT PASSED, stop here with a ranked list of fixes. If PASSED and I
confirm, tag `v2.0.0`.

## Part 2: refactor (commit units)

1. **`refactor(db): make verdict append-only with iteration and is_current`**
   A new verdict for the same requirement is a new row; exactly one row per requirement is current.
   Existing rows are migrated as iteration 0.

2. **`refactor(db): add assessment state machine and score range`**
   The states from §3.1 as an enum, a transition table in code, and one function per transition
   that refuses an illegal move. Lower and upper score bounds on the assessment; until v3 they are equal.

3. **`feat(db): add hr_question, question_waiter and hr_rule tables`**
   With the vector on `hr_question`, and scope, version, status and `supersedes` on `hr_rule`.
   The judge prompt gains a rules section, empty for now.

4. **`feat(api): accept answers to questions on endpoint 3`**
   The payload type and its validation. The behavior behind it arrives in 3.3; until then an answer
   to a question that does not exist returns a clear error.

5. **`refactor(services): extract the service layer`**
   REST handlers become thin. Everything that REST, the resolver tools and MCP will call lives in
   service functions with typed inputs and outputs and no HTTP types.

## Done when

- [ ] The gate result is recorded with numbers, `pipeline_version` and run count.
- [ ] After the refactor, variant A on the dev split served from the LLM cache gives the same verdicts and scores as before.
- [ ] All existing tests pass without weakening any assertion.
- [ ] An illegal state transition raises an error (test), and every legal transition from §3.1 is covered.
- [ ] No REST handler contains a SQL query or pipeline logic.

## Traps

- This is a behavior-preserving refactor. If a number changes, something broke; find it before going on.
- Migrate data, do not drop it. Assessments from v1 and v2 must survive with their verdicts.
- Do not build question handling, the validator or the resolver here. Tables and seams only.
