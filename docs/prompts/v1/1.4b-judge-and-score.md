# Phase 1.4b: Judge, quote checking, score

**Read first:** §1.1, §2.4 (steps 6–8 and the score formula), §3.2 (the two quote checks), §4.4
("Channel separation", "Architecture"), §4.5, §7 ("Refactor before v2") of `docs/plan.md`.
**Depends on:** 1.4a.
**Branch:** `phase/1.4b-judge`

## Goal

The core of v1: one judge call per CV–position pair returns a verdict and a verbatim quote for
every requirement, code checks the quotes and computes the score, and the first accuracy baseline
is measured.

## Build (commit units)

1. **`refactor(pipeline): introduce ContextPack and build_context`**
   The judge receives a `ContextPack` from `build_context()`. In v1 it holds the whole masked CV,
   the computed tenure facts, the requirements, and an empty slot for rules. In v2 only this
   function changes.

2. **`feat(pipeline): add judge prompt and verdict schema`**
   One LLM call per pair. Per requirement: `met`, `partial` or `not_met`, the verbatim quote or
   quotes, a short rationale. Prompt order: instructions, rubric, then the CV in a fenced data
   block that the system message declares inert. `thinking_level` low. The judge has no tools.
   If a requirement is missing a verdict or has two, call the judge once more, then fail the job.

3. **`feat(pipeline): verify quotes against the cv text`**
   A quote passes if it exists verbatim after normalization, or with a `rapidfuzz` score of at
   least 90 (threshold in configuration); numbers in the quote must exist verbatim. `met` or
   `partial` without a quote is flagged. In v1 a flagged verdict stays as the judge gave it, keeps
   its flag, and its quote is not shown as evidence. There is no re-judging until v3.

4. **`feat(pipeline): compute score and ranking order`**
   `met` 1, `partial` 0.5, `not_met` 0. Weighted coverage separately for mandatory and nice-to-have
   requirements, then `100 × (0.7 × mandatory + 0.3 × nice-to-have)`. A failed mandatory
   requirement sets a flag, and flagged candidates rank below unflagged ones.

5. **`feat(worker): add judge and re-judge jobs with assessment reuse`**
   One assessment per candidate–position pair and `rubric_version`. The same CV submitted again
   with the same posting costs no LLM call. The re-judge job from 1.2 now does its work.

6. **`feat(api): add ranking and assessment read endpoints`**
   Ranked list per position; one assessment with its verdicts, quotes, flags and character offsets
   into `raw_text`. An assessment made against an unconfirmed rubric carries that label.

7. **`docs(eval): record v1 baseline`**
   Run variant A on the dev split, fix what the failures show, then run the test split once and
   record the numbers.

## Out of scope

The validation loop, the verifier, re-judging and the `needs_rule` field (v3). Retrieval (v2).
The interface (1.5).

## Done when

- [ ] Verdict accuracy on the test split is measured and recorded as the baseline. Target ≥ 80%.
- [ ] Every quote the API returns as evidence exists in the CV; the share of flagged verdicts is recorded.
- [ ] Score unit tests cover: all met, all not met, a failed mandatory requirement, a posting with
      no nice-to-have requirements, and a parent–child pair.
- [ ] Editing a position's requirements re-scores its CVs without a manual step (carried over from 1.2).
- [ ] Submitting the same CV and posting twice makes zero additional LLM calls.
- [ ] The eval-failure-reviewer subagent has reviewed the dev failures, and its top causes are in `docs/PROGRESS.md`.

- **No nice-to-have requirements.** The formula would cap the score at 70. Propose the renormalization.
