# Phase 1.1a: Skeleton (Compose, database, job queue)

**Read first:** §2.5, §6.3 and the v1 table in §7 of `docs/plan.md`; `docs/schema.sql` if it exists.
**Depends on:** phase 0.
**Branch:** `phase/1.1a-skeleton`

## Goal

A running skeleton: Postgres in Docker, migrations, an API that answers a health check, a worker
that takes jobs from a Postgres queue, and a frontend scaffold. No PDF handling and no LLM yet.

## Build (commit units)

1. **`feat(infra): add postgres with pgvector, settings, db pool and health endpoint`**
   `compose.yaml` with a `postgres` service: image `pgvector/pgvector:pg17`, `shared_buffers` 512 MB,
   a healthcheck, a named volume, the host port taken from an env variable.
   Settings through `pydantic-settings`. A psycopg 3 connection pool. FastAPI app with
   `GET /health` that reports database connectivity. `make up`, `make down`, `make api`.

2. **`feat(db): add alembic baseline with v1 tables`**
   Tables needed in v1: `job_position`, `requirement`, `candidate`, `document`, `ranking_request`,
   `request_candidate`, `assessment`, `verdict`, `task_queue`. If `docs/schema.sql` exists, take the
   DDL from it and leave out v2 and v3 tables and columns. If it does not, derive the columns from
   §2.5 and §2.4 and show me the DDL before writing the migration.
   Columns the plan needs from day one: `document.raw_text`, `job_position.source_sha256`,
   `job_position.rubric_version`, `job_position.rubric_status`. `make migrate`.

3. **`feat(queue): add task queue with skip-locked claiming, retries and stale requeue`**
   A queue module over `task_queue`: enqueue with `dedup_key`, claim with `FOR UPDATE SKIP LOCKED`,
   complete, fail with an attempt counter (three attempts, then `failed` with the error stored),
   and requeue of jobs stuck in `running` longer than a visibility timeout.
   A worker process (`python -m ats.worker`, `make worker`): polling loop, a handler registry keyed by
   job type, graceful shutdown on SIGINT and SIGTERM, and a `noop` handler for tests.

4. **`feat(web): scaffold vite react typescript app with api health check`**
   `web/` with Vite, React, TypeScript strict and TanStack Query. One page that shows the API health.
   A dev proxy from the web server to the API. ESLint and a typecheck script, both added to `make check`. `make web`.

5. **`chore(infra): add api, worker and web services to compose`**
   Dockerfiles and Compose services for `api`, `worker` and `web` behind a profile, so `make up`
   starts Postgres alone and `make up-all` starts everything.

## Out of scope

File upload, PDF extraction, any endpoint beyond `/health`, the `vector` extension and `chunk`
table (phase 2.1), the question and rule tables (phase 2.6).

## Done when

- [ ] `make up && make migrate` creates the nine tables on an empty database.
- [ ] `make api` serves `GET /health` with status 200 and the database reported as reachable.
- [ ] Integration tests prove the queue: two concurrent claimers never get the same job; a repeated
      `dedup_key` does not create a second job; a job that fails three times ends as `failed`;
      a job left in `running` past the timeout is claimed again.
- [ ] Killing the worker in the middle of a job loses nothing: after restart the job completes.
- [ ] `make web` shows the health status from the API.
- [ ] `make up-all` brings up all four services.
- [ ] `docker stats` memory per service is recorded in `docs/PROGRESS.md`.

## Traps

- The API process must stay light: no model loading, no heavy imports at startup (§6.3 RAM budget).
- Alembic needs SQLAlchemy only as its engine. Do not introduce ORM models; migrations are SQL.
- If port 5432 is taken on the host, do not stop the other service. Use another port through the env variable.
