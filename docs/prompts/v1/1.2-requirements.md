# Phase 1.2: Requirements (LLM client, extraction, endpoint 3, confirm screen)

**Read first:** §1.1 ("Requirements: extraction"), §2.0, §2.4 ("Position setup"), §4.5, §6.1 of `docs/plan.md`.
**Depends on:** 1.1b.
**Branch:** `phase/1.2-requirements`

## Goal

The first LLM call in the project. A posting PDF becomes a list of atomic requirements that HR
can edit and confirm through endpoint 3 and a screen.

The plan lists `LLMClient` under phase 1.4, but this phase already calls the model, so the client
is built here.

## Build (commit units)

1. **`feat(llm): add LLMClient with gemini adapter, rate limiting, 429 retry and response cache`**
   A thin `LLMClient` interface and one adapter on `google-genai`. Structured output from a
   Pydantic schema. `thinking_level` as a per-call parameter. A rate limiter set by `LLM_RPM`,
   with an injectable clock so tests do not sleep. Retry with backoff on 429. A response cache
   keyed by the hash of model, prompt and parameters. Each call returns tokens in, tokens out,
   latency and the cache hit flag. A `FakeLLMClient` for tests.
   Read the current `google-genai` documentation for structured output, thinking configuration
   and the model id before writing the adapter.

2. **`feat(pipeline): extract atomic requirements with parent links`**
   Prompt version 1 as a file under `src/ats/prompts/`. Input: the whole posting text.
   Output schema per requirement: text, mandatory or nice-to-have, weight, `min_months` when the
   requirement states a duration, and a `parent` reference when it refines another requirement
   from the same posting. A compound requirement is split at extraction. `thinking_level` minimal.

3. **`feat(worker): add position setup job`**
   Triggered when endpoint 1 creates a new position: extract the posting text, call the
   extraction, write the `requirement` rows. An existing position (same `sha256`) skips all of it.

4. **`feat(api): add POST /hr/answers for requirement confirmation and edits, plus position reads`**
   Two payload types. Confirm sets `rubric_status` to `confirmed`. Edit replaces the requirement
   list, increases `rubric_version`, and enqueues re-judge jobs for the position's assessments.
   Both are idempotent through `dedup_key`. Read endpoints: list positions; one position with its requirements.

5. **`feat(web): add requirement edit and confirm screen`**
   Positions list. Per position: an editable table of requirements (text, type, weight,
   minimum months, parent), add and remove, a Confirm button, the rubric status and version.

## Out of scope

The list of likely ambiguities from §2.4 step 3 (phase 3.5). The re-judge handler itself (1.4b):
this phase only enqueues the job. Requirement embeddings (2.1).

## Done when

- [ ] Uploading a posting creates requirements with status `unconfirmed`.
- [ ] A posting that asks for "Java" and "3 years of experience in Java" yields two requirements,
      the second pointing to the first; "a degree and 3 years of experience" yields two requirements.
- [ ] Confirm changes the status to `confirmed`. An edit increases `rubric_version` by one and
      enqueues re-judge jobs; a repeated identical request does neither twice.
- [ ] A rate limiter test: at 5 requests per minute the sixth call waits for the next window (simulated clock).
- [ ] A 429 response is retried; a second identical call is served from the cache without a request.
- [ ] No test calls the real model. One manual smoke run against Gemini is recorded in `docs/PROGRESS.md`.

## Carried over

- "Editing requirements re-scores that position's CVs" needs the judge: verified in 1.4b.
Add both to "Carried over" in `docs/PROGRESS.md`.

## Traps

- The rate limiter is in-process. That is correct while there is one worker; say so in a comment
  and in `docs/PROGRESS.md`, because a second worker would need a shared limiter.
- Prompt order matters for caching (§4.5): instructions first, the posting text last.
- The posting is not masked and not chunked (§2, §2.4). Requirements are the unit.
