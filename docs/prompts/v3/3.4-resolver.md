# Phase 3.4: Resolver (agent with tools)

**Read first:** §1.3 (the paragraph on workflow versus agent), §3.1, §3.3, §3.4, §3.6 (reasons for the manual version), §6.1 ("Function calling") of `docs/plan.md`.
**Depends on:** 3.3.
**Branch:** `phase/3.4-resolver`

## Goal

The one agent in the system: for a flagged requirement, the model chooses whether to look for
more evidence, apply an existing rule, or ask HR. Written by hand, with hard budgets.

## Build (commit units)

1. **`feat(resolver): add the seven tools over the service layer`**
   `search_cv`, `get_cv_section`, `compute_experience`, `search_rules`, `find_similar_rulings`,
   `ask_hr`, `submit_verdict`, with the signatures from §3.3. Each is a typed function over a
   service; none takes a candidate or position argument.

2. **`feat(resolver): add the tool-calling loop with gemini function calling`**
   Through `google-genai`, using the SDK's handling of multi-step tool calls. The orchestrator
   binds the candidate and the position; the model cannot choose them. `ask_hr` and
   `submit_verdict` end work on the requirement. A submitted verdict goes through the checks again.

3. **`feat(resolver): enforce budgets and stopping conditions`**
   At most 4 tool calls per requirement and 12 per assessment, within the 30,000-token budget of
   the assessment. When a budget is spent, the requirement keeps its flag and the assessment goes
   to `needs_review` with the reason. Nothing is accepted silently.

4. **`feat(worker): route flagged requirements through the resolver`**
   The `resolving` state from §3.1: back to `judging`, on to `waiting_hr`, or to `needs_review`.

5. **`feat(eval): add resolver metrics`**
   The share of flagged requirements resolved without HR, the accuracy of those, tool calls per
   requirement, and tokens per resolved requirement.

## Out of scope

LangGraph (3.6). The "does this question matter" filter (3.5). Tools for external sources.

## Done when

- [ ] A test proves the tool budget is never exceeded, including when the model keeps asking for more.
- [ ] Every tool call appears in the trace with its arguments and result.
- [ ] The share of flagged requirements resolved without HR is measured and recorded.
- [ ] A test proves the resolver cannot read another candidate's chunks, whatever arguments the model sends.
- [ ] A verdict from `submit_verdict` that fails a check does not become final.

## Traps

- In a multi-step tool call the response carries a thought signature that must go back unchanged
  (§6.1). The SDK does this; a hand-built request without it returns a 400. Read the current documentation first.
- Tool results contain CV text. Return them as structured data marked as untrusted, the same way the judge receives the CV.
- `find_similar_rulings` only suggests an answer for HR. It never applies another position's rule by itself.
- Keep the loop in plain Python: a state enum, a transition table, a function per state (§3.6). No framework in this phase.
