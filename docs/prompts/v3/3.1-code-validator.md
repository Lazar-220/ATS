# Phase 3.1: Code validator

**Read first:** §1.3 (points 1–3), §3.2, §5.1 ("3. Loop" row), §5.3 of `docs/plan.md`.
**Depends on:** v2 gate passed and refactor merged (2.6).
**Branch:** `phase/3.1-code-validator`

## Goal

Deterministic checks flag suspicious verdicts, their precision and recall are measured on planted
errors, and variant B is compared with variant A.

## Build (commit units)

1. **`feat(validation): add code checks and flags`**
   The five code checks from §3.2: exactly one verdict per requirement; `quote_not_found`;
   `no_evidence`; `duration_mismatch` (a requirement's `min_months` against the computed tenure);
   `contradiction` (related requirements with incompatible verdicts). Flags are stored per verdict.
   The assessment moves through `validating` using the state machine from 2.6.

2. **`feat(eval): add planted-error set`**
   Correct assessments with one planted error each: a fabricated quote, a verdict without evidence,
   a contradiction, a wrong tenure. Include the same case in another language and script.
   Labels: which check should fire, and on which requirement.

3. **`feat(eval): add validator precision and recall`**
   Per check and overall.

4. **`feat(eval): add variant B and verdict-change accounting`**
   Variant B is variant A plus the code checks. For each variant against A: fixed (incorrect to
   correct), broken (correct to incorrect), lateral; net gain; the share of assessments with at least one flag.

5. **`docs(eval): record validator metrics and A versus B`**

## Out of scope

The LLM verifier and re-judging (3.2), questions to HR (3.3), the resolver (3.4).

## Decision to bring to me before implementing

The plan defines variant B as "A + code checks" but not what happens to a flagged verdict when
there is no verifier or resolver yet. Propose the deterministic handling per flag (for example:
`duration_mismatch` is corrected by code from the computed tenure; `quote_not_found` and
`no_evidence` send the assessment to `needs_review` without changing the verdict), and what that
means for B's accuracy number.

## Done when

- [ ] Validator precision and recall on the planted set are measured and recorded, per check.
- [ ] The A versus B table is recorded with fixed, broken, lateral and net gain.
- [ ] The share of assessments that carry at least one flag on the clean test split is recorded.
      Above 40% means the checks are oversensitive (§5.3).
- [ ] Nothing is accepted silently: every flag is visible on the verdict in the API and the interface.

## Traps

- The fuzzy threshold of 90 from 1.4b is a starting value. Calibrate it on the planted set (§6.3) and record the chosen value.
- A flag is not a verdict change. Keep the judge's verdict and the flag as separate facts.
- Tenure checks need the requirement's `min_months`. If extraction left it empty for requirements
  that state a duration, fix extraction, not the check.
