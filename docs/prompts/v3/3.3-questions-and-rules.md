# Phase 3.3: Questions to HR and versioned rules

**Read first:** §1.3 (points 4–5), §3.1, §3.2 (`needs_rule` row), §3.4, §3.5, §4.4 ("Persistence"), §5.1 ("3. Loop" row) of `docs/plan.md`.
**Depends on:** 3.2.
**Branch:** `phase/3.3-questions-rules`

## Goal

When a requirement does not define a situation, the system asks HR once per position, keeps
working on other CVs, and applies HR's answer as a versioned rule to everyone affected.

## Build (commit units)

1. **`feat(pipeline): add needs_rule to the judge output and rules to the prompt`**
   The judge does not rate its confidence. It describes the situation the requirement does not
   define. Active rules of the position go whole into the prompt's rules section; the judge
   records which rule it applied.

2. **`feat(services): add question creation with deduplication`**
   Under an advisory lock per position–requirement pair, look for a similar open question by the
   embedding of the situation description. If one exists, add the verdict to `question_waiter`;
   otherwise create the question. The question text is assembled from a template and structured
   fields, never from raw CV text. At most five open questions per position; beyond that the
   verdict becomes `partial` and the assumption is recorded in the rationale.

3. **`feat(worker): pause and resume assessments around questions`**
   The verdict becomes `pending_hr`, the assessment moves to `waiting_hr` with a score range from
   the worst to the best outcome, and the worker takes the next job. No process waits.

4. **`feat(services): turn an answer into a rule and re-judge everyone affected`**
   One transaction: write the rule, close the question, increase `rubric_version`, enqueue
   re-judge jobs for every waiter and for earlier completed assessments of the position.
   Re-judging covers only that requirement, with the rule in the prompt, and records `applied_rule_ids`.
   Editing a rule creates a new version with `supersedes`; the old one becomes `superseded`, and the
   same re-judging runs. A position's rule takes precedence over a company rule; a newer version over an older one.

5. **`feat(web): add questions inbox, answer form and rule history`**
   Open questions per position with the situation and options; the answer form; the rule versions.
   The ranking shows a range for assessments that are waiting, ordered by the lower bound.

6. **`test: add the four scenario tests`**
   The scenarios in "Done when", scripted with the fake client.

## Out of scope

The resolver (3.4): here a `needs_rule` report leads straight to a question. Rubric lint and the
"only if it changes the shortlist" filter (3.5). Rule retrieval (the plan: only above 50 rules).

## Done when

- [ ] 20 CVs with the same ambiguity produce exactly one question.
- [ ] After the answer, all 20 are judged with no manual step.
- [ ] A 21st CV with the same case in another script opens no question; the rule is applied.
- [ ] Editing the rule re-judges the affected assessments and keeps the full history of rules and verdicts.
- [ ] A repeated answer submission changes nothing (idempotent through `dedup_key`).
- [ ] A test proves no text from a CV can enter a rule, and none reaches the question as free text.

## Traps

- Deduplication needs a similarity threshold. Calibrate it on paraphrased and cross-language pairs,
  and record the false merges and the misses.
- Two workers must not create the same question. The advisory lock is the mechanism; test it with concurrent calls.
- The "21st CV in another script" passes only if the rule's situation description matches across
  scripts. Check how the judge gets the rule: the whole list goes into the prompt, not a similarity search.
- A job that sits in `running` too long returns to the queue (§3.5). Make sure a resumed job does not ask the question again.
