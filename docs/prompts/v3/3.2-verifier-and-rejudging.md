# Phase 3.2: Verifier and re-judging

**Read first:** §1.3 (points 1–3), §3.1, §3.2 (the verifier row), §3.4, §5.3 (all of it) of `docs/plan.md`.
**Depends on:** 3.1.
**Branch:** `phase/3.2-verifier-rejudging`

## Goal

An isolated verifier and a bounded re-judging loop, and a measured answer to the question the
plan asks: does the loop improve the scores, or is it an expensive majority vote?

## Build (commit units)

1. **`feat(validation): add isolated verifier`**
   The same model, in a separate call. It sees only the requirement, the quotes and the computed
   facts; never the CV and never the judge's rationale. It answers whether the quote supports the
   verdict. A negative answer sets `not_supported`. It runs after the code checks, only on verdicts they did not flag.

2. **`feat(validation): add bounded re-judging of flagged requirements`**
   Only the flagged requirement is judged again, with the flag as feedback. At most two rounds per
   assessment. Stop on no progress: the same check failing twice for the same requirement.
   A budget of 30,000 tokens per assessment. Every stop leaves a flag and leads to `needs_review`.
   Each round appends a verdict row with its iteration.

3. **`feat(eval): add variants C and D`**
   C is B plus the verifier and re-judging. D is the control: three judge passes and a majority
   vote, at about the same number of tokens as C. Per variant: accuracy, macro-F1, fixed, broken,
   lateral, net gain, tokens per net fixed verdict, the share of assessments that enter the loop,
   and the gain of round two relative to round one.

4. **`feat(eval): add paired significance tests`**
   McNemar and a bootstrap interval for the accuracy difference, on the same items. Three runs per variant.

5. **`docs(eval): record the A/B/C/D table and the decision`**

## Out of scope

Questions to HR (3.3), the resolver and its tools (3.4). In this phase a requirement that is still
flagged after two rounds goes to `needs_review`.

## Done when

- [ ] The A/B/C/D table is in `docs/PROGRESS.md` with net gain, cost and the bootstrap interval for C against D.
- [ ] The decision is recorded: keep the loop, narrow it, or drop it, using the rules in §5.3. I make
      the decision; you present the table and a recommendation.
- [ ] A test proves the verifier's prompt contains no CV text beyond the quotes and no judge rationale.
- [ ] A test proves the loop never exceeds two rounds or the token budget.
- [ ] Re-judging one requirement leaves every other requirement's current verdict untouched.

## Traps

- This is the most expensive eval in the project: four variants, three runs each. Show the dry run,
  propose a cheaper first pass on a subset, and wait for my confirmation. Use the batch path from 2.4 if it exists.
- The verifier shares the judge's blind spots, because it is the same model (§5.3). That is why D exists. Do not skip D.
- The judge can yield to the critic and change a correct verdict (§1.3). "Broken" is the number to watch.
- With about 250 test verdicts, draw the conclusion from the interval, not from the difference of means.
